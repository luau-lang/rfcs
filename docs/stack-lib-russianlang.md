# Runtime stack library

## Summary

Библиотека для манипулирования стеком коррутины на уровне языков с явным управлением, в виде ограниченной адресуемости execution continuations.

## Motivation

Why are we doing this? What use cases does it support? What is the expected outcome?

Сегодня чтобы перейти из функции A в Б нужно вернуть явный return, но если таких функций много? Если таких функций еще больше чем много? Возможно нам пригодится поведение схожее с goto из Си, но более безопасное и менее назойливое. Эта библиотека дает возможность Luau использовать управляемую нелинейную передачу управления между участками Lua-исполнения, не заставляя пользователя протаскивать return, yield, callbacks, состояния и дополнительные continuation-объекты через каждый уровень вызовов. По сути она решает это:

```md
A() -> B() -> C()
            -> if a then return else b
        -> if c then b else return
    -> if if if if if if if if .................... else return SPECIAL_SIGNAL if SPECIAL_SIGNAL then return if SPECIAL_SIGNAL then return if SPECIAL_SIGNAL then return if SPECIAL_SIGNAL then return
```

Обычный Lua control flow хорошо выражает локальное выполнение: вызов → результат → возврат. Но когда решение, принятое глубоко внутри execution tree, должно изменить дальнейшее выполнение существенно выше, приходится вручную строить протоколы и огромные деревья однотипного рутинного кода, который только мешает нам потом понимать "а че вообще делать, тут 92394 протоколов сигнализации, а мне код ИИ писать надо" - stack предоставляет отдельный механизм именно для таких случаев.

Также мы сможем представить execution stack как программируемую структуру, а не только как результат call/return. Обычная VM рассматривает stack преимущественно как историю вызовов. Библиотека предлагает использовать его ещё и как пространство управления. То есть execution state становится адресуемым.

Дать нелокальное управление, но сохранить границы безопасности. Основная идея stack — сделать нелокальное управление пространственно ограниченным текущим execution context:

```md
    StackContext
    ├── A
    │    ├── mark("X")
    │    └── B
    │         └── C
    │              └── goto("X")
    │
    └── lock()
        └── D
            └── X недоступен
```

То есть мотивация здесь ещё и в том, чтобы получить что-то мощнее return, но безопаснее произвольного C goto. Библиотека stack предназначена не для замены return или coroutine, а для предоставления языку явного механизма управления нелинейным execution flow, когда обычной модели call/return недостаточно. В современных Lua-подобных VM execution state почти полностью определяется текущим CallInfo и линейной историей вызовов. stack исследует альтернативную модель, в которой execution state может сохраняться, адресоваться и продолжаться независимо от обычного жизненного цикла отдельного CallInfo.

Библиотека stack не является расширением coroutine API. Это альтернативная модель управления execution state, построенная поверх coroutine runtime. Его основная стоимость и преимущество заключается не в количестве изменяемых файлов, а в том, что VM должна начать поддерживать lifetime execution state независимо от обычного lifetime CallInfo, что позволит пользователям успешно использовать механизмы с высоким уровнем сложности.

То есть, концептуально, решается такая проблема:

```md
                     Runtime Stack
                            │
            ┌──────────────┴──────────────┐
            │                             │
    Context Transfer              Execution Graph
            │                             │
    mark / hit / goto / on / lock   enter / reentered / split
            │                             │
    нелокальный переход             изменение структуры
    ancestry                         execution
    boundaries                      re-entry
                                    branching
```

## Design

This is the bulk of the proposal. Explain the design in enough detail for somebody familiar with the language to understand, and include examples of how the feature is used.

Для разработки этой библиотеки нужно иметь несколько `struct`, которые позволяют нам правильно перемещаться
в пространстве. Это, как минимум, `StackContext`, `StackMark` и `StackContinuation`. Для части функционала надо будет изменить `CallInfo`, добавить данных в `Frame`, возможно сделать `StackBranch`. 

Для пользовательского опыта дизайн гораздо проще, чтобы разобраться в его функционировании достаточно прочитать дальйшее описание:

Сама библиотека:

```luau
    declare type stack = {
        read mark: (name: string) -> ()
        read hit: (name: string) -> (boolean, ...any)
        read goto: (name: string, ...any) -> ()

        read reentered: () -> (boolean, ...any)
        read enter: (layer: number?, ...any) -> ()

        read count: () -> number
        read lock: (name: string?) -> ()

        read on: (that: ((...any) -> (...any)|any)|thread) -> boolean
        read split: () -> (boolean, ...any)
    }
```

Большая часть вопросов которые решает эта библиотека касается функционального стиля программирования, но за счет своего контекста позволяет расширить варианты выполнения функций до еще большего размера. По сути от результатов в дочерних функциях можно отталкиваться также, как если бы это был Си `goto label`. Это естественно приведет как к положительным сторонам, так и к тотальной анархии если неправильно использовать это, но сам инструмент может быть крайне полезным как минимум для логических элементов.

Я крайне НЕ рекомендую считать, что здесь все сразу взаимозаменяемое. Нет, это неверно в корне, и мало того, разные части библиотеки потребуют существенные изменения в LVM если пытаться их структуировать и прототипировать сразу. Разделите ее на 2 части: слой передачи контекста выполнения (mark/hit/goto/lock/on) и слой СТРУКТУИРОВАНИЯ ГРАФОВ ИСПОЛНЕНИЯ (split/enter/reentered). Для понимания и реализации будет проще именно передача контекста выполнения, вторая часть достаточно проста но невероятно сложна в реализации. В Drawbacks об этом будет очень много сказано.

Заранее: для всех функций работа с Си функционалом или функционалом через userdata недоступна, это `внутренние` вызовы LVM и внутренняя обработка LVM. Продолжения стека могут пересекать фреймы выполнения Lua, но должны завершаться на границах среды выполнения, не допускающих повторного входа.

Далее примеры.


```luau

    const state, out = stack.split()
    -- Представим такую ситуацию, функция выполняется в середине своего контенкста: этот вызов заставит
    -- функцию считать, что она разделилась на ДО и после
    -- split() создаёт дочернее continuation state, которое совместно использует доступные
    -- lexical/environment references, но имеет независимое instruction position и execution storage
    --
    -- На примере это будет:
    --
    ```luau
        local function foo()
            local run = coroutine.running()
            local x = 1
            local y = 2

            const state, out = stack.split()

            local z = 3

            if stack.on(run) then
                print ("Мы выполняемся в sub coroutine", state, out, x, y, z)
                -- Вывод будет: string, nil, nil, number, number, number
                -- Это потому что state и out на тот момент не существуют, и никогда не могли существовать
                -- А вывод xyz будет корректным
            else
                print("мы выполнили sub coroutine и теперь можем безопасно обработать ее", state, out)
                -- Вывод будет: string, boolean, any, number, number, number
                -- Единственная разница, что x и y будет возможно переопределить в sub coroutine, а вот
                -- z всегда статически будет 3 после конца выполнения sub coroutine, так как и там и тут
                -- переменная z объявляется сразу после stack.split() или в другом месте после, что
                -- заставляет нас переопределять новую переменную на контекст
                --
                -- Если бы z была const, то она была бы одинаковой для любого контекста, и тоже самое
                -- касается x и y, потому что const - безопасная граница. Это можно или игнорировать,
                -- потому что z так и так можно просто переопределять как для sub coroutine так и для
                -- main coroutine, так и использовать в качестве оптимизации, потому что переменную
                -- легко засунуть в общий буфер - она все равно никогда не изменится. Но это касается
                -- только значений, которые компилятор знает статически, если ранее мы знали что там
                -- напрямую стоит number или string  или иное значение которое НЕ является ссылочным типом
                --
                -- Для ссылочных типов действует строгое правило, что все ссылки которые именно СОЗДАЮТСЯ
                -- на объект в пространстве, который ранее не существовал: table, userdata, thread и тп, -
                -- всегда будут ссылаться на новый уникальный объект. Проще говоря, если до stack.split()
                -- мы наблюдали local/const ссылку на ссылочный объект, то мы ее просто получаем и ничего,
                -- а иначе мы создаем новый объект
            end
        end
    ```
    -- 
    -- Это предоставляет нам возможность писать опасный код и там же его и обрабатывать без участия протокола
    -- защиты типа pcall/xpcall, потому что падающая коррутина не будет ронять stack своего исходника, тем
    -- самым обеспечивая высокую нелинейность программируемого кода там где это необходимо

    const is = stack.on(function or thread)
    -- Возвращает boolean результат, находится ли в стеке данная функция/коррутина или нет
    -- Проще говоря, для переданных функций проверяется именно то что они находятся в предыстории
    -- смотря от текущего положения коррутины, а для коррутин проверяется, что их предыстория происходит
    -- от определенной коррутины. То есть если ранее объявить run = coroutine.running() и после stack.split()
    -- или coroutine.run(coroutine.create(function () end)) передать внутри функции stack.on(run), то будет
    -- получен результат true, потому что коррутина по предыстории находится там
    --
    -- Исключениями являются операции типа pcall/xpcall и task. В task достаточно просто встроить работу
    -- stack.lock(), о которой будет ниже, а для pcall/xpcall будет автоматически применяться stack.lock()
    -- вызываемых ими функций. Почему так?
    --
    -- Дело в том что переход по stack коррутины требует соблюдения безопасности как самой коррутины, так и
    -- ее личного пространства для продолжения стабильной работы. Участок выполнения, который мы сознательно
    -- оборачиваем в pcall/xpcall заставляет нас расценивать, что следующий участок может быть крайне опасным
    -- для нашего существования, а следовательно позволять ему видеть наши временные метки и подниматься по
    -- stack за края защитного поля нельзя. Данный участок будет видеть только свой stack: это означает, что
    -- вызов stack.on() для функций будет недоступен. Однако это не касается коррутин, потому что мы можем
    -- вытащить коррутину как closureup значение и сравнить ее прямо внутри кода, coroutine.running() == run
    --
    -- По сути, вызов stack.on() внутри pcall/xpcall не будет выбрасывать ошибки, но для функций будет всегда
    -- результат false, если они были вызваны за барьером

    stack.mark(string)
    -- В функционале Си существует семантика goto label , что позволяет статически прыгать программе по
    -- разным областям выполнения и исполнять разнообразные операции. Это крайне небезопасная штука является
    -- крайне серьезным инструментом, stack заинтересован в том чтобы его реализовать
    --
    -- Реализация этой фичи обеспечивается тем, что в коррутине на текущий stack по указанной метке будет
    -- сохраняться весь текущий frame относительно положения stack.mark() в пространстве. Объявленные здесь
    -- is будут сохранены всегда, пока stack коррутины имеет в себе этот контекст. Как только коррутина 
    -- покидает этот контекст - освобождение памяти остается таким же как и раньше, и GC спокойно может
    -- уничтожить этот frame
    --
    -- Для того чтобы обеспечить безопасность, функционал типа
    ```luau
        local function foo()
            stack.mark("A")
        end

        local function bar()
            stack.goto("A")
        end
    ```
    --
    -- будет ограничен: мы не можем переопределить одну и туже марку после ее объявления,
    -- она всегда будет true после достижения, но только для той части дерева stack коррутины,
    -- которая находится в части где была объявлена stack.mark(), сразу после нее, или ниже
    -- по stack коррутины. Если мы попробуем все таки переопределить эту метку снова, нам
    -- выбросит error("cannot reuse an already defined label in the space")
    --
    -- По сути, stack.mark() создает `execute from A with continuation environment` точку в
    -- пространстве коррутины

    const is, out = stack.hit(string)
    -- Мы можем проверить, не перебирались ли мы ранее на эту метку, а заодно получить аргументы
    -- от этой операции
    --
    -- Поскольку метка доступна для объявления всего 1 раз, stack.hit() работает также как и функция
    -- stack.reached() - она запоминает контекст перемещения только для этой функции, и при попытке
    -- вытащить stack.hit() вне функции где был объявлен stack.mark - вернет false, потому что
    -- для функции ниже той где была объявлена stack.mark() эта пространственная метка не существует,
    -- либо она не принадлежит ей, что больше подходит

    stack.goto(string, ...any)
    -- Операция goto заставляет коррутину бросить текущий контекст: все операции которые выполнялись
    -- до этого момента теряются, но только до полученной метки. Коррутина по stack будет помнить, что
    -- она ранее заходила в какую-либо sub coroutine или функцию, это будет можно вывести через stack.on()
    -- Однако, получить все значения в пространстве видимости того времени будет нельзя, stack.goto()
    -- передает только то что получил в variadic своих аргументов, и будет таскать это и только это
    --
    -- Если попытаться перейти на марку объявленную за stack.lock(), либо попытаться перейти на марку
    -- если мы находимся в контексте pcall/xpcall и эта марка находится ЗА ним, то мы получим ошибку
    -- вида error("stack elevation above the limit is not available in a secure environment")
    --
    -- Когда мы переходим по stack.goto(), frame коррутины который был сейчас уничтожается, и мы
    -- перемещаемся на пространственную метку stack.mark() с ее состоянием в тот момент
    
    stack.enter(nil or 0 or number, ...any)
    -- Если мы получаем nil или 0, то мы поднимаемся на 1 ступень и сразу же входим в ту же функцию,
    -- откуда был вызван stack.enter(). Если мы получаем 1, то мы поднимаемся на 2 ступени и входим в
    -- по стеку на функцию, которая вызвала функцию где определен stack.enter(), при этом мы можем
    -- передать любые значения, но никак не значения которые были для этой линии в моменте stack.enter()
    --
    -- У этой функции есть ограничения, мы можем подняться на уровень выше только 80 раз, как если бы
    -- мы пытались запустить task 80 раз, - лимит не даст нам уйти в бесконечную рекурсию или вечные
    -- вызовы, которые заставят потерять нас управление над текущим контекстом. Это выбросит ошибку
    -- error("the limit of stack raises is exceeded")
    --
    -- Функция не даст подняться по stack коррутины за барьер pcall/xpcall, мы получим ошибку вида
    -- error("stack elevation above the limit is not available in a secure environment")
    --
    -- Отрицательные значения возвращают ошибку вида error("can't move on a stack that doesn't exist")
    -- Значения которые уходят за глубину stack.count(), то есть превышают количество поднятий,
    -- которые коррутина реально может осуществить по своему stack, а по сути это количество stack
    -- шагов, вернет ошибку вида error("an attempt to move along the stack to where there is nothing")
    --
    -- У этой функции нет родства с stack.mark()/stack.goto()/stack.hit(), это отдельный механизм.
    -- Кроме того, данная функция будет заставлять GC хранить текущий FrameContext для захода в 
    -- исполнителей выше по stack, а значит освобождение данных будет доступно строго после
    -- того как коррутина убьет нижний stack frame. Либо все эти значения стоит считать closureup, потому
    -- как 

    const is, out = stack.reentered()
    -- У нас есть представление о том что делает stack.mark() и stack.goto(), - они по сути работают
    -- как способ поднятия по stack коррутины и позволяют нам путешествовать в пространстве stack так,
    -- что мы могли бы стать мета-путешественниками и выполнять совершенно разные операции там где мы хотим
    --
    -- Функция возвращает stack.reentered() для каждой функции отдельно. То есть, она берет по сути
    -- debug.info(2, "f"), и проверяет, не заходила ли коррутина в эту же функцию ранее. Это действует
    -- в контексте только той функции, куда был выполнен stack.enter(), а вот функции дальше по stack или
    -- коррутины - вернут false, если конечно в них не был заход stack.enter()
    --
    -- Функция не вернет true если был переход через stack.goto(), для этого есть stack.hit()
    -- Кроме того, функция не реагирует на рекурсивные заходы, она реагирует только на stack.enter()

    stack.lock()
    -- Все эти операции позволяют нам свободно путешествовать по stack коррутины. Однако они лишают нас
    -- безопасности выполнения наших операций. Это может привести к тому, что где-то в далеком коде был
    -- объявлен stack.mark("1"), а потом где-то внизу мы делаем этот же stack.mark("1") и программа
    -- падает с ошибкой о переопределении марок.
    --
    -- Либо мы пытаемся ходить по stack коррутины там, где нам нельзя ходить: пробуем пройтись по ее
    -- защищенным местам или выполнить небезопасный код там, где это недопустимо
    --
    -- Чтобы избежать такого, stack.lock() отсекает поле видимости для функций и контекста выполнения
    -- ниже stack.lock() по stack самой коррутины. Это даст нам право переопределять ранее объявленные 
    -- stack.mark(), но запретит нам 
    --
    -- Если вызвать stack.lock() на имя метки, то его поведение будет таким же как и ранее только для
    -- этой метки, то есть на нее нельзя будет прийти снова. Это позволит также освободить ресурсы с
    -- этой метки

```

Для более простого понимания, предлагаю формализовать VM-модель четырьмя сущностями. Я думаю, это значительно упростит весь RFC:

```md
    Activation
        текущее выполнение функции

    Continuation
        сохранённое состояние Activation

    Boundary
        предел, через который нельзя проходить

    Context
        дерево доступных Continuation
```

Тогда:

```md
    mark()
        create Continuation

    hit()
        inspect Continuation state

    goto()
        discard descendants + resume Continuation

    on()
        inspect ancestry

    lock()
        create Boundary

    up()
        resume ancestor Activation

    reentered()
        inspect Activation identity

    split()
        clone Continuation
```

## Drawbacks

Why should we *not* do this?


Функционал позволяет расширить управление собственным кодом до уровня, частично схожего с C `goto`, но цена такого расширения крайне высока. Это не обычное API-расширение стандартной библиотеки и даже не изолированная возможность coroutine: для полноценной реализации требуется изменить существенную часть виртуальной машины и определить новые правила существования execution frame.

Для начала, подобное изменение требует абсолютно огромного изменения доброй части LVM:

```md
VM/src/lstate.h
    CallInfo / lua_State / StackContext
VM/src/lstate.cpp
    new/rem runtime state
VM/src/ldo.h
VM/src/ldo.cpp
    stack goto/enter/reenter
    continuation management
    frame unwinding
    boundary handling
VM/src/lvm.h
    internal stack runtime API
VM/src/lvmexecute.cpp
    interpreter integration
    dispatch
    reentry/goto exits
VM/src/lgc.cpp
VM/src/lgc.h
    marking StackContinuation / StackBranch
    thread relations
VM/src/lfunc.cpp
VM/src/lfunc.h
    upvalue / closure interactions
VM/src/lapi.cpp
Compiler/src/
    new bytecode operations
CodeGen/src/
    native/JIT handling
    deoptimization
```

Возможно нужно добавить еще больше операций или изменить поведение еще сильнее: НЕ ФАКТ, что native codegen или JIT смогут это обрабатывать, - хотя native codegen может реализовать прыжки по операциям, JIT может ВООБЩЕ не реализовывать это, потому что это буквально прыжок к другим инструкциям обратно по пространству stack коррутины.

И это только то, что приходит на ум. Фактически изменения затронут ещё больше участков runtime, поскольку существующий Luau предполагает достаточно строгую модель жизни CallInfo: вызов создаёт frame, выполнение движется вперёд, return уничтожает соответствующее состояние, а stack и upvalue корректируются в соответствии с обычным жизненным циклом функции.

Но stack.mark() ломает это предположение. После создания метки execution frame потенциально должен оставаться доступным для нелокального продолжения. Следовательно, VM должна понимать разницу между frame, который больше не используется обычным исполнением, и frame, который уже покинут, но всё ещё является частью существующего continuation.

То есть GC уже нельзя рассматривать только как сборщик Lua-объектов. Runtime должен дополнительно отслеживать сохранённые execution state и гарантировать, что они не держат указатели на уже недействительные stack slots, CallInfo, open upvalues или другие VM-структуры.

Особенно сложным становится stack.split(). В этом случае появляется уже не сохранённая точка входа, а несколько одновременно существующих execution paths. Они могут иметь общие Lua-объекты, closures и upvalues, но при этом обладать независимым pc, CallInfo и состоянием локальных значений. Это фактически требует от VM поддержки ветвления continuation state.

Это немедленно усложняет управление памятью. Мало того, GC должен понимать связь между этими состояниями и не освобождать один execution context раньше другого. Open upvalues становятся отдельной проблемой, потому что они могут ссылаться непосредственно на stack slots.

Кроме этого, нужно определить, что происходит с побочными эффектами. stack.split() не может сделать полноценную копию мира программы: Обе ветки могут продолжать ссылаться на один объект state. Следовательно, копируется execution state, но не состояние окружающего мира. Это создаёт сложную модель семантики. Без очень строгой спецификации пользователи будут ожидать от split() полноценного snapshot/clone coroutine, хотя фактически это будет только разделение исполнения. 

Отдельная проблема — stack.goto() и stack.enter() не являются обычными переходами по bytecode. stack.goto() способен уничтожить несколько активных CallInfo и восстановить состояние более старого continuation. stack.enter() способен не просто вернуться к caller, а заново запустить более старый frame. Luau VM больше не может предполагать, что control flow движется только по 3 ранее известным путям, появляется дополнительная ось. Это усложняет практически все места, где runtime предполагает последовательность call/return, включая yield/resume, error handling, protected calls, C continuations и debugger integration.

Особенно опасен pcall/xpcall. Они уже являются границами обработки ошибок и continuation. Добавление ещё одного механизма нелокального перехода означает, что runtime должен строго определить, через какие protected boundaries разрешено перемещение, а через какие нет.

То же касается task, yieldable C functions, coroutine.resume() и любых других механизмов, которые могут сохранять продолжение выполнения. Compiler также становится сложнее.

Если stack.mark("A") превращается в runtime-visible label, compiler больше не может свободно считать произвольную часть локального control flow недостижимой. Ему нужно понимать, что некоторый участок bytecode может быть достигнут нелокальным переходом.Compiler должен гарантировать, что состояние x, доступное continuation, действительно соответствует установленной семантике. При оптимизациях нельзя просто переместить, устранить или переиспользовать локальное состояние так, как если бы существовал только обычный linear control flow.

То есть stack.mark() становится фактически compiler-visible control-flow barrier. debug и debugger tooling тоже усложняются. После stack.goto() execution history и current call chain перестают быть одним и тем же понятием. Отладчику придется выводить специальный внешний вид для этого.

Есть и проблема определения идентичности frame. После stack.enter(), stack.goto() - что является одним и тем же frame?

Есть и более фундаментальный архитектурный недостаток: этот механизм резко увеличивает количество допустимых control-flow путей. То есть сложность анализа программы становится существенно выше. Это особенно важно для статического анализа, оптимизатора и самого пользователя. Код становится мощнее, но одновременно теряет значительную часть локальной предсказуемости. Также существует риск получить очень плохие failure modes Runtime должен ограничивать не только глубину обычного Lua call stack, но и количество continuation, reentry, branches и возможных переходов между ними. Иначе новая система может создавать циклы управления, которые невозможно выразить обычными call/return, причём без очевидного места, где именно должна остановиться рекурсия.

Наконец, появляется очень высокая стоимость поддержки. Даже если первая реализация будет работать, каждое последующее изменение VM потребует проверять совместимость с новым execution model. Практически любое изменение, затрагивающее CallInfo, stack, upvalues, yield или continuation, потенциально может сломать stack.

Поэтому это не просто новая возможность языка. Это постоянное обязательство runtime поддерживать вторую, существенно более сложную модель control flow. В результате главный недостаток предложения заключается не в том, что stack трудно реализовать один раз. Главный недостаток заключается в том, что после его реализации вся VM становится обязана учитывать существование нелинейного управления исполнением.

Это очень высокая архитектурная цена ради возможности, которая в большинстве программ будет не нужна. Здесь я бы особенно оставил последнюю мысль: главный drawback — не «много файлов надо изменить», а то, что после этого `CallInfo` перестаёт быть внутренней деталью обычного call/return механизма и становится частью нелинейной модели исполнения. Это очень большое архитектурное обязательство для LVM. Поэтому CallInfo не должен становиться долгоживущим объектом

## Alternatives

What other designs have been considered? What is the impact of not doing this?

Расширить `debug.info()`, добавив туда информацию обо всех переданных аргументах в функцию, расширить `coroutine`, добавив туда `coroutine.on`, так как метод фактически принадлежит `coroutine` ибо завязан на операциях с ними. Вообще вся `stack` библиотека является сборником использования `debug` и `coroutine` библиотеки и может быть реализована даже сегодня. Единственным таким механизмом является `error`, потому что его можно перехватить через `pcall/xpcall` и не дать коррутине умереть, тем самым выполнив нужную задачу, но это на сегодняшний день является обходом

Но есть и другие варианты:

Самый простой вариант — не менять VM вообще и передавать специальный результат наверх:

```luau
    local result = C()

    if result == SPECIAL_SIGNAL then
        return SPECIAL_SIGNAL
    end

    -- ... и на каждом уровне возврата спец сигналов

    local result = B()

    if result == SPECIAL_SIGNAL then
        return result
    end
```

Это полностью соответствует существующей модели Lua и не требует изменений runtime. Цена — именно та проблема, ради которой предлагается stack: каждый промежуточный уровень обязан знать о существовании специального control-flow протокола. При большом execution tree это быстро превращается в шум из return, проверок статусов и дополнительных структур. По сути это самый безопасный вариант, но он плохо масштабируется по глубине и количеству независимых сигналов.

Другой вариант — использовать существующий механизм ошибок как нелокальный goto: `error(SIGNAL)`

и затем:

local ok, result = pcall(run)

Это уже позволяет перескакивать через произвольное количество Lua-фреймов, не протаскивая результат через каждый return. Именно поэтому error в некотором смысле является уже существующим аналогом части stack.goto().

Однако это семантически неправильное использование error handling. Ошибка становится не сообщением об ошибке, а обычным механизмом управления. Кроме того, такой подход связан с unwind semantics, взаимодействует с pcall/xpcall, traceback и protected boundaries и не предоставляет адресуемого execution state. Нельзя нормально выразить независимые mark, hit, split или enter как части единой модели. То есть это наиболее близкий существующий workaround, но не полноценная альтернатива архитектуре stack. Есть даже попытка реализации именно этого механизма (я не проверял ее):

```luau
    --!strict

    const stack = {}

    do
        type userdata_proxy_link = any
        type user_function = (...any) -> ...any
        type layer = number

        type catch_internal_type = {
            read catch_up: number,
        }

        const create_ltype = newproxy
        const transfer_raise = error
        const unexpected_error = error
        const unexpected_assert = assert

        const ltype: string = type(create_ltype())
        const layers = {} :: { [userdata_proxy_link]: number? }
        const links = {} :: { [userdata_proxy_link]: user_function? }
        const f_layers = setmetatable({} :: { [user_function]: { layer? }? }, table.freeze({ __mode = "ks" }))

        const try_catch_selected_function = function(): user_function
            local i = 1

            while true do
                i += 1

                const try_catch_needle_function = debug.info(i, "f")
                const T = type(try_catch_needle_function)

                if T == "function" then
                    if f_layers[try_catch_needle_function] then
                        return try_catch_needle_function
                    end

                    break
                elseif T == "nil" then
                    break
                end
            end

            return unexpected_error("cannot enter, there is no registered function in the stack")
        end

        const catch_xpcall_err = function(err: unknown)
            if type(err) ~= ltype or not links[err] then
                unexpected_error(err)
            end

            const f = unexpected_assert(links[err], "unexpected catch type")
            const f_layer = unexpected_assert(f_layers[f], "unexpected function")
            const expected_layer = layers[err]

            if expected_layer then
                const pos = table.find(f_layer, expected_layer)
                if pos then
                    table.remove(f_layer, pos)
                else
                    stack.raise(expected_layer)
                    layers[err] = nil
                    links[err] = nil
                    return
                end
            else
                table.remove(f_layer)
            end

            if #f_layer == 0 then
                f_layers[f] = nil
            end

            layers[err] = nil
            links[err] = nil
        end

        @checked
        function stack.define<T..., U...>(layer: number?, f: (T...) -> U..., ...: T...): U...
            const f_layer: { number? } = f_layers[f] or {}
            table.insert(f_layer, layer)
            f_layers[f] = f_layer

            return table.unpack({ xpcall(f, catch_xpcall_err, ...) :: any }, 2)
        end

        @checked
        function stack.raise(to_layer: number?)
            const link = create_ltype()
            const stack_function_caller: user_function? = try_catch_selected_function()

            links[link] = stack_function_caller
            layers[link] = to_layer

            transfer_raise(link)
        end
    end

    return stack

```

Можно явно представлять продолжение:

```luau
    A(function(...)
        B(function(...)
            C(function(...)
                ...
            end)
        end)
    end)

    -- или хранить continuation в отдельных объектах:

    local continuation = {
        run = function(...) ... end
    }
```


Это уже гораздо ближе к модели, которую фактически скрывает stack. Вместо изменения VM пользователь самостоятельно представляет continuation как данные. Преимущество в том, что такой код не требует специальных возможностей runtime и потенциально может быть реализован поверх обычного Lua. Недостаток — continuation становится частью прикладного API. Пользователь должен вручную создавать, передавать, хранить и вызывать их. В результате библиотека управления execution flow превращается в явную CPS-архитектуру, а именно необходимость постоянно протаскивать continuation через дерево вызовов stack и пытается устранить.

Нелинейное выполнение можно представить как конечный автомат:

```luau
    local state = "C"

    while state do
        if state == "A" then
            ...
            state = "B"
        elseif state == "B" then
            ...
            state = "C"
        elseif state == "C" then
            ...
            state = "A"
        end
    end
```

Это вариант для сложных сценариев, AI, parser pipelines и workflow-систем. Главное преимущество — control flow становится явно представленным данными, а не скрыт в runtime.

Но это уже другая модель программирования. Она хорошо подходит для заранее известных состояний, но значительно хуже подходит для локального произвольного дерева вызовов. stack пытается сохранить обычный синтаксис функций и добавить нелокальное управление поверх него, тогда как state machine заставляет пользователя заранее моделировать граф выполнения.

Часть задач можно решить созданием нескольких coroutine и координацией через coroutine.resume, yield, события или очереди сообщений.

Например:
```luau
    local worker = coroutine.create(function()
        ...
        coroutine.yield(...)
        ...
    end)
```

В таком случае execution state уже является объектом, который можно сохранить и продолжить.

Это важный аргумент в пользу существующего coroutine API: Lua уже имеет понятие suspended execution state.

Однако coroutine не дают нелокального перехода внутри одного execution tree. resume продолжает конкретную coroutine с места yield, а не позволяет находящемуся глубоко внутри C() перенести управление в заранее объявленный mark("A").

То есть coroutine решают проблему сохранения execution state, но не проблему адресуемого перехода между его частями.

Можно сделать API примерно такого вида:

```luau
    local continuation = stack.capture()

    continuation:resume(...)
    continuation:cancel()
```

В отличие от stack.split(), continuation тогда становится обычным userdata/object, которым управляет пользователь.

Это значительно проще концептуально для VM: вместо того чтобы делать весь execution stack адресуемым, runtime сохраняет только конкретную continuation.

Цена — пользователь должен самостоятельно управлять lifetime этих объектов. Кроме того, становится сложно выразить операции вроде: `stack.goto("A")`, потому что вместо пространственной адресации появляется объектная модель `continuation_A:resume(...)` - Это уже больше похоже на first-class continuations, чем на stack traversal.

Другая фундаментальная альтернатива — реализовать в языке полноценные first-class continuations:
```luau
    local continuation = callcc(function(k)
        ...
    end)

    continuation(...)
```

Тогда проблема решается на более общем уровне: continuation становится объектом языка и может сохраняться, передаваться и повторно запускаться. С точки зрения выразительности это даже мощнее части предложенного stack. Но именно поэтому это ещё тяжелее для Lua-подобной VM. Возникают те же проблемы с сохранением frame, local state, upvalue, GC, yield, protected calls и native boundaries. Кроме того, call/cc вводит гораздо более сильную семантику, чем требуется для большинства предполагаемых сценариев stack.

stack фактически можно рассматривать как ограниченную, структурированную форму continuations, где доступ к ним определяется положением в execution tree и существующими security boundaries.

Ещё одна альтернатива — добавить обычные VM-инструкции перехода: `JUMP`, `JUMP_IF` - или специализированный runtime opcode для нелокального выхода. Это может быть полезно для compiler-generated control flow, но почти бесполезно для поставленной задачи как пользовательский API.

Обычный jump работает внутри одного frame/control-flow graph. Он не решает задачу:

`C -> B -> A`

когда C должен перенести выполнение в состояние A, сохранённое ранее. Для этого всё равно потребуется continuation/frame management, то есть простое добавление `JUMP` проблему не решает.

Часть proposal действительно можно прототипировать уже сейчас через:

```luau
    debug.info()
    debug.traceback()
    coroutine.running()
    coroutine.create()
    coroutine.resume()
    pcall()
    xpcall()
    error()
```

Например, stack.on() можно приблизительно реализовать анализом текущего call chain, а stack.hit() и некоторые варианты mark() — таблицей контекстов. Это полезно именно как proof-of-concept: можно проверить API и usability без изменения LVM.

Но здесь существует фундаментальное ограничение: debug API позволяет наблюдать execution state, но не позволяет безопасно восстановить произвольный старый execution state. Мы можем узнать, что функция присутствует в истории вызовов, но не можем сказать VM: уничтожь текущие CallInfo и продолжи этот старый frame с его локальным состоянием.

Поэтому debug API подходит для прототипирования семантики on/hit, но не для реализации настоящего goto/enter/reentered/split.

Вместо изменения VM можно попытаться преобразовать пользовательский код компилятором. Можно трансформировать в явную state machine:

```luau
    while true do
        if pc == 0 then
            ...
        elseif pc == 1 then
            ...
        elseif pc == 2 then
            ...
        end
    end
```

Тогда stack.goto("A") превращается в изменение pc.

Это потенциально интересный компромисс. Runtime остаётся почти неизменным, а сложная модель управления реализуется на уровне compiler IR. Но есть серьёзный недостаток: таким способом очень сложно сохранить исходную семантику Lua locals, closures, upvalues, debug.info, coroutine, yield и native calls. Кроме того, stack предполагает возможность пересекать обычные Lua call boundaries, а compiler transformation работает только там, где compiler видит и преобразует соответствующий код.

Итого, варианты:

```md
                        VM cost     expressiveness     safety
    return              none        low                high
    error               none        medium             medium
    CPS                 none        high               high
    state machine       none        high               high
    stack               high        high               medium/high
    call/cc             extreme     very high          low
```

В итоге существует несколько классов альтернатив: явная передача результатов, exception-based unwinding, CPS/continuation objects, coroutine orchestration, state machines, compiler transformation и полноценные first-class continuations/effects. Первые не требуют изменения VM, но заставляют пользователя вручную моделировать execution flow. Последние дают необходимую выразительность, но приходят примерно к той же проблеме, ради которой существует stack: VM должна хранить и управлять execution state независимо от обычного call/return lifetime.

Поэтому stack не является единственным возможным решением. Его отличие состоит в выборе конкретной точки компромисса: execution state остаётся частью обычного Lua execution model, но получает ограниченную адресуемость и структурированные нелокальные переходы. При этом mark/hit/goto/lock/on могут рассматриваться как отдельный слой безопасной передачи control context, тогда как split/enter/reentered требуют значительно более глубокого изменения continuation model.

Если stack не реализовывать, Lua сохраняет более простую и предсказуемую call/return модель, а разработчику приходится использовать существующие механизмы — return, error, coroutine, callbacks, CPS или собственные state machines. Это существенно дешевле для VM, но сложные нелинейные execution graphs остаются ответственностью пользовательского кода.


## Examples

Добавление этой библиотеки в LVM является очень неприятной задачей. Несмотря на то что тут достаточно четко обусловлена работа всего ожидаемого кода, я считаю должным показать примеры, почему это вообще должно быть, и ради чего придется страдать:

Предположим:

```AI
 └─ Planner
     └─ Executor
         └─ Action
             └─ validation
                 └─ resource check
```
resource check обнаруживает: "нужно полностью сменить стратегию" -При обычной модели ему нужно знать, как сообщить это через: `Action`, `Executor`, `Planner`. То есть нижний слой начинает знать о протоколе верхних слоёв. stack позволяет этому коду обратиться к execution context напрямую: `stack.goto("retry_planning")` -  это решает класс проблем cross-layer control signaling.

Предположим, нам нужно отделение control flow от data flow. Обычный Lua передаёт данные через `return result`, и эти данные одновременно используются как механизм управления: `if result == SPECIAL then ...`

Получается смешение: data + control flow

Библиотека позволяет разделить:

данные:
    return value

управление:
    stack.goto("X")

То есть специальный переход не обязан становиться специальным значением, протоколом или userdata.

Предположим, нуюна программируемая история исполнения

stack.on() решает этот класс: `stack.on(foo)` - то есть: находится ли foo в ancestry текущего execution context? Это полезно, когда поведение зависит не только от текущей функции, но и от того, как именно она была достигнута.

Например:

```md
    request
    └─ AI
        └─ behavior
        └─ action
```

и код внутри action может различать: action вызван из AI execution, или action вызван независимо - это уже класс задач execution-context introspection.

Предположим, нам нужен ранний выход из сложных алгоритмов без exception semantics. Есть целый класс алгоритмов, где error() технически подходит, но семантически неправилен.

Например:
```md
    parser
    validator
    AI behavior tree
    workflow
    transaction
    resource acquisition
    search algorithm
```

Внутри: `D -> обнаружил успешный результат` -> надо прекратить большой объём вложенного поиска. Можно сделать: `error(SUCCESS)` и ловить это через pcall, как сейчас предлагает пример реализации `goto/mark`, но тогда успешный control transfer выглядит как ошибка.

stack.goto() позволяет выразить: "я не ошибся; я изменил маршрут исполнения". Это отдельный класс non-error exceptional control flow.

Предположим, нам нужно управление графами исполнения


Нам нужно решать не просто вопрос call tree, а execution graph. В обычной модели: `A -> B -> C -> return`. Следовательно, может появиться:

```md
      A
     / \
    B   B'
    |    |
    C    D
     \  /
      ...
```

То есть execution state начинает рассматриваться как программируемый граф. Это уже задача из области:

```md
continuations
coroutine scheduling
workflow execution
stateful interpreters
control-flow graphs
```

Но здесь, начинается совершенно другой уровень сложности.

Впрочем эти примеры конечно интересные, а вот какие есть у нее нерешаемые задачи, хотя похоже что она решает их? Она не является хорошей заменой:

```md
    return
    coroutine
    async/await
    event system
    state machine
    message passing
    exception handling
```

Она нужна тогда, когда необходимо именно:
```md
    глубоко внутри текущего execution tree
            ↓
    изменить дальнейшее выполнение
            ↓
    без ручного протаскивания этого решения
            ↓
    через каждый промежуточный вызов
```

up/reentered добавляют re-entry в существующие activation, а split добавляет ветвление execution state. Это уже не одна и та же проблема, а следующие уровни этой модели.
